# Pixso — единый макет Android UI

Файл: https://pixso.net/app/design/4T8MYI6qqkQjlqe3MKJY7Q?icon_type=1

## Структура

31 канонический редактируемый фрейм, 35 сценариев Android, 70 ключей захвата (35 × 2 темы). Реестр schema 2: `design/pixso-sync.json`. Снимки обеих тем сохраняются как входные данные CI, но больше не требуют отдельных фреймов.

- 00 · Index & Sync — указатель и правила работы.
- 01 · Foundations & Components — переменные и компоненты.
- 02 · App screens — основные экраны и реальные состояния.
- 03 · Flows & states — диалоги, формы и сценарии.

Две архивные страницы удалены по запросу пользователя, после проверки отсутствия master-компонентов и ссылок на них из рабочих фреймов. Сохранены ID 31 канонического фрейма. Старые ID записаны как previous_frame_id для истории, не использовать для редактирования.

## Темы

Коллекция `01 / Semantic color` (2:2), режимы Light (2:0), Dark (24:7544). Новые семантические токены имеют префикс Theme/. Выберите секцию или отдельный фрейм и измените режим переменных. По умолчанию секции Light, дочерние фреймы наследуют режим. Не создавать отдельные фреймы для тем. Сохранены исходные переменные Light/* и Dark/* для совместимости существующей библиотеки.

Геометрия единая — за основу взят светлый вариант. Если захват Android содержит разные координаты шторки в двух темах (например security), это не повод дублировать экран: проверить причину в приложении и при необходимости обновить общий макет. Полное попиксельное соответствие после реорганизации не подтверждено.

## Компоненты и состояния

- App / Bottom navigation (24:7763): Selected, пять вариантов.
- App / Statistics tabs (24:9195): Tab, четыре варианта. stats-stores, stats-products, stats-trend используют statistics с соответствующим Tab.
- App / Product row (24:9276): State, три варианта (With price, Without price, Two-line subtitle). Название, описание и цена редактируются в текстовых слоях экземпляра. API объединения TEXT-свойств вариантов не сработал, поэтому не использовать неподтверждённые property keys.
- login-form использует welcome. Различные по структуре состояния (пустой/заполненный список, разные формы, раскрытый архив, шторки) сохранены.

## Инкрементальная синхронизация

1. CI формирует PNG, XML, layout.json и `pixso-sync-input/plan.json`. Планировщик поддерживает schema 1 (старый) и 2 (текущий).
2. В schema 2 `targets` — уникальные канонические фреймы; `screens` — ссылки на захваты, каждый содержит target_key, frame_id, theme_mode и при необходимости variant_overrides. План группирует captures по target_key. Работать с каждой группой один раз, не создавать отдельный экран для темы, другого текста или выбранной вкладки. Для нового сценария сначала определить, есть ли существующий общий экран.
3. Обновлять существующие слои, общие компоненты и Theme/* переменные. При проверке переключить режим темы и вариант вкладки; затем восстановить исходный режим/вариант.
4. Статус verified и last_verified с хэшами присваивать каждому захвату только после фактического сравнения. Без проверки сохранять draft. CI пропускает только захваты с подтверждёнными хэшами.
5. Планировщик формирует входные файлы; отдельный CI выполняет двустороннюю синхронизацию сопоставленных цветов. Структурные правки требуют проверки.


## Автоматический CI (двусторонняя синхронизация)

### Подключение

В Pixso: профиль → User Center → Personal Access Token → Generate Token.
В GitHub: Settings → Secrets and variables → Actions → New repository secret.
Имя секрета: `PIXSO_ACCESS_TOKEN`. Значение: токен Pixso с доступом редактирования именно этого файла. Не хранить его в репозитории или логах. Официальный Remote MCP: https://pixso.net/developer/en/mcp/remote-mcp.html, адрес https://pixso.net/mcp, заголовок Token.

Workflow: `.github/workflows/pixso-sync.yml`.
- push UI/ресурсов в beta: автоматически проверить и синхронизировать сопоставленную палитру;
- расписание: каждый час в :17; GitHub запускает расписание на default branch main, где расположен только диспетчер, отправляющий workflow_dispatch в beta;
- ручной запуск: Actions → Pixso bidirectional sync → Run workflow → beta. apply=true выполняет безопасные правки; apply=false делает только отчёт. release=true запрашивает подписанный beta APK после успешной синхронизации. accept_structure=true применять только после проверки соответствующей реализации.

### Текущая база и ограничения

`design/pixso-baseline.json` снят с текущего реального Pixso после оптимизации: 31 канонический фрейм, 35 сценариев, 70 ключей захвата в реестре; 18 Theme/* токенов, 3 общих набора компонентов. `scripts/pixso-snapshot.js` считывает идентификаторы, свойства, геометрию, текст, привязки и варианты и вычисляет контрольные значения. Повторный снимок подтвердил стабильность контрольных значений. Это контрольная база структуры, не доказательство визуального соответствия.

`scripts/pixso-sync.py` выполняет трёхстороннее сравнение последней базы, живого Pixso и Theme.kt. Сопоставленные семантические цвета обновляются в существующих переменных/ролях, без дублирования экранов. При конфликте, неизвестном токене или структурной правке запись прекращается. Отчёт: artifact pixso-sync-report/report.json. После успешной синхронизации новый baseline и при необходимости Theme.kt коммитятся только в beta; обычная синхронизация запрашивает UI-захват, release=true — beta релиз. Никакие старые FIG-файлы не импортируются.

Изменение геометрии, текста, новых слоёв, компонентов и Compose-структуры пока требует переноса по макету с учётом бизнес-логики и визуального сравнения. CI обнаруживает изменения Pixso, а отдельный UI handoff формирует данные об изменениях Android по каноническому реестру. Для принятия реализованной структурной правки после проверки запустить accept_structure=true; это обновляет контрольную базу, не статус verified. Не использовать флаг для скрытия конфликта цветов или неподдерживаемых токенов.

Проверка: семь тестов синхронизации успешно выполнены в GitHub Actions. Живой CI-доступ к Pixso и запуск последующей сборки ещё не проверены — требуется PIXSO_ACCESS_TOKEN. Подключение текущего чата не заменяет авторизацию GitHub Actions.

## App / Empty state — перенос из Pixso

Новый набор 27:2137 (Theme=Light/Dark) зарегистрирован в schema 2; 10 экземпляров в 10 канонических фреймах. В Compose единая функция FreshCutEmptyState: 96 dp / radius 32 dp, иконка 24 dp, Theme/Surface = palette.card, отступ 20 dp, заголовок 23/28 sp SemiBold, описание 14/24 sp Regular, интервал 8 dp, letterSpacing 0,5 sp. Блок текста минимум 60 dp, описание опционально. Контент может переноситься на узком экране/при увеличении системного шрифта. Используется в покупках, каталоге (включая отсутствие результатов поиска), архиве, статистике и уведомлениях; фоновые состояния наследуются через те же экраны. Состояние «Все товары куплены» отдельно и не изменено. Две темы используют LocalPalette, а не два Kotlin-компонента. Baseline не принят до визуальной сверки новой сборки; статус draft.

## Центрирование App / Empty state

Компонент Compose занимает всю предоставленную область между верхними элементами и нижними действиями/навигацией. Единые горизонтальные отступы 20 dp, симметричные вертикальные 8 dp. Каталог при отсутствии результатов отдаёт весь вес свободной области пустому состоянию, а не пустому LazyColumn; кнопка создания товара остаётся внизу. В Pixso центрированы 10 экземпляров на существующих ID, включая фоновые сценарии. Координаты вычислены по границам существующих верхних/нижних элементов, расстояния сверху и снизу равны с точностью 0,05 dp. Темы используют одну геометрию; контрольный снимок после сборки ещё требуется.

## Тексты App / Empty state

Короткие заголовки и пояснения к каждому состоянию хранятся в Android string resources. В Pixso обновлены свойства Title, Description, Show description десяти существующих экземпляров и текст двух мастер-вариантов. Поиск без результатов использует тот же компонент с отдельным текстом, без нового фрейма. Геометрия и центрирование сохранены. Статус draft до сверки Android-захвата.

## Статусы CI при изменениях структуры

Структурное изменение без конфликтов палитры — ожидаемый результат проверки, не техническая ошибка. Workflow выводит предупреждение review required, сохраняет отчёт, пропускает запись и запуск сборки из задания синхронизации. Контрольная база не меняется. Конфликты цветов, неизвестные токены и ошибки подключения/выполнения остаются ошибками CI. После визуальной сверки структуры использовать явное accept_structure=true. Независимый workflow Android по-прежнему может собирать beta по push.

Создание своего товара, пагинация, выбор другого товара, добавление штрихкода и вспомогательные действия поиска используют FreshCutSecondaryButton. Динамические состояния, которых не было отдельными фреймами, представлены примерами, без дублирования рабочих экранов. ## Правила структуры
- 00 · Index & Sync: правила и покрытие.
- 01 · Foundations & Components: общая библиотека исходных компонентов и переменных.
- 02 · App screens: покупки, каталог и магазины, архив, статистика, профиль.
- 03 · Flows & states: авторизация, добавление, уведомления, настройки, группы, администрирование.
- 90/91 · Archive: исходные экраны и сценарии (не менять).
- Имя экрана и стабильный ключ: light/<screen> или dark/<screen>. Секции группируют состояния; темы рядом.
- Не создавать страницы на каждый номер версии, не заменять фрейм целиком, не вставлять скриншот как слой. Использовать существующие компоненты, размеры Compose, Manrope.

## Обновление
1. CI формирует план `pixso-sync-input/plan.json` и исходные файлы для действий create/update_in_place/register_new. План строится до удаления неизменённых снимков из UI handoff.
2. В Pixso найти frame_id и обновить редактируемые слои на месте. Для отсутствующего фрейма создать его один раз в указанной секции и записать ID в реестр. Не удалять отсутствующие в захвате состояния.
3. Сверить с PNG, измерениями layout.json и XML. После проверки записать status=verified и last_verified={commit, hashes} из плана. Без подтверждения не помечать verified.
4. Следующая сборка пропускает только состояния с совпадающими хэшами последнего проверенного макета, а не предыдущего CI. Любые расхождения в исходных файлах отправляются на пересмотр (консервативно, включая нестабильные XML/JSON).

CI создаёт пакет входных данных, но не пишет в Pixso самостоятельно: доступ редактирования предоставлен через текущий чат. Для автономной записи нужен отдельно подтверждённый API/авторизация Pixso. Покрытие 70 состояний подтверждено по инвентарю Pixso, но точное визуальное соответствие приложению и полнота всех возможных сценариев приложения не подтверждены.
