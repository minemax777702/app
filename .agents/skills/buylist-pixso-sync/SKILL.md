# Список покупок: синхронизация Kotlin ↔ Pixso

## Подключение и границы

- GitHub: `minemax777702/app`, рабочая ветка `beta`. Не менять `main`, stable, production Supabase или релизы без отдельного запроса.
- Pixso: https://pixso.net/app/design/4T8MYI6qqkQjlqe3MKJY7Q?icon_type=1. Это единственный рабочий макет. Подключить GitHub и Pixso через доступные инструменты; в Codex допустим локальный checkout и настроенный Pixso Remote MCP. Никогда не запрашивать значение `PIXSO_ACCESS_TOKEN` в чате и не выводить его в логи.
- В начале прочитать актуальные `AGENTS.md`, `design/PIXSO_SYNC.md`, `design/pixso-sync.json`, при необходимости `design/pixso-baseline.json`, исходники затронутых Compose-компонентов и живые узлы Pixso. Не использовать устаревшее число экранов, прошлые ID или скриншоты из переписки вместо актуального реестра.
- Код определяет поведение, данные и доступность. Pixso определяет визуальный контракт. Основное направление текущей разработки — код → Pixso. Явная ручная правка макета — Pixso → код. При несогласованных изменениях с обеих сторон не перетирать ни одну сторону: выделить конфликт и сохранить независимые правки.

## Как исполнять задачу

1. Зафиксировать HEAD beta, прочитать текущий реестр schema 2, проверить доступ к живому файлу и последним CI-артефактам. По возможности сравнить снимок Pixso с baseline. Найти все использования изменяемого компонента, включая формы, bottom sheets, empty/loading/error, фильтры, меню, состояния поиска, ветки прав доступа. Не ограничиваться первым найденным экраном.
2. Выбрать минимальный общий компонент/вариант. При новом UI сначала сверить/создать визуальный контракт в Pixso, затем реализовать Compose. При правке исходников обновить существующие соответствующие слои Pixso; при правке макета перенести размеры, палитру, типографику, тексты и структуру в Compose. Сохранять бизнес-логику, динамические данные, действия, валидацию, accessibility, IME, локализацию и поддержку API 29+. Тексты выносить в string resources, размеры — в общий компонент/метрики. Не повышать minSdk.
3. Править обе стороны непосредственно доступными инструментами. Не ограничиваться планом или отчётом. Перед массовой записью проверить узлы, компоненты, шрифты и переменные; применять небольшие согласованные партии с readback. При отсутствии доступа честно указать, какая сторона не обновлена; не имитировать синхронизацию.
4. Обновить `design/pixso-sync.json` и `design/PIXSO_SYNC.md`, при необходимости Index & Sync и сценарии `scripts/capture-ui.py`/fixture seed. Применять стабильные ID. Для новых структурных состояний зарегистрировать target и capture keys обеих тем. Для текстовых/цветовых/вариантных изменений переиспользовать target. Новые сценарии должны быть достижимы через реальные действия ADB и тестовые данные; проверять контекст, не только общий текст кнопки.
5. Проверить исходники, импорты, ресурсы, типы, размеры и ограничения. Проверить визуально реальные Pixso screenshots, включая обе темы, и Android PNG/XML/layout.json именно из сборки изменённого commit. При отсутствии артефакта не ставить verified. Исправлять обнаруженные ошибки в рамках задачи.
6. Сохранить согласованный коммит в beta без force push; при конфликте HEAD перечитать и объединить. Если запрос не предполагает выпуск, выполнить проверку/захват без публикации. Если пользователь просит beta-релиз, запустить подписанную beta-сборку после правок; не публиковать stable. Сверить фактический статус GitHub Actions и результаты, не объявлять успех по факту запуска.
7. Коротко сообщить: что изменено в коде и Pixso, покрытие сценариев, commit, CI/сборка, что не подтверждено. Не задавать повторных вопросов, если данные уже известны. При ограничении времени/инструментов сохранить завершённые части и указать конкретный остаток.

## Правила макета

- Четыре существующие страницы: Index & Sync, Foundations & Components, App screens, Flows & states. Не восстанавливать архивные страницы или старый FIG. Размещать новые уникальные сценарии в подходящей существующей секции.
- `targets` — канонические фреймы, `screens` — ссылки на захваты. Несколько capture keys могут ссылаться на один frame_id. Light/Dark — режимы одной коллекции `01 / Semantic color`, токены `Theme/*`. Не дублировать целые экраны ради темы, текста, цен или вкладки. Использовать variants/instance overrides и сохранять общие редактируемые слои.
- Переиспользовать актуальные компоненты из shared_components: навигация, вкладки, карточки, empty state, кнопки, формы и сценарии магазина. Не отсоединять экземпляры без необходимости. При изменении высоты bottom sheet сохранять привязку к нижнему краю. Не менять системные глифы и палитру без основания.
- Полноэкранный Empty state центрируется в свободной области с одинаковыми отступами; плитка и размер иконки берутся из текущего мастер-компонента. Не показывать крупное пустое уведомление в компактном попапе, если уже есть действие создания/добавления. При введённом запросе без совпадений — краткая подсказка. Не смешивать отсутствие данных, загрузку и ошибку.
- Дизайн в двух темах, русский UI, минимализм, монохромные иконки, общие кнопки и шторки. Новая структура только для действительно нового интерфейса, не для каждого значения данных.

## CI, сверка и безопасность

- Существующий `.github/workflows/pixso-sync.yml` автоматически проверяет UI-изменения и по расписанию сверяет живой Pixso с последним принятым baseline. `scripts/pixso-sync.py` реализует двустороннюю синхронизацию сопоставленных цветов; `scripts/pixso-snapshot.js` считывает структуру. Не утверждать, что произвольная геометрия или Compose генерируются CI автоматически. Для структурных правок исполнитель обязан внести изменения на обеих сторонах.
- При ручном аудите можно запустить `gh workflow run pixso-sync.yml --ref beta -f apply=false` (или эквивалент доступного GitHub-инструмента). Для захвата без релиза — `gh workflow run figma-redesign-apk.yml --ref beta -f publish=false`. Для подписанного beta — `publish=true` только если запрошено. Проверять актуальные inputs workflow перед запуском.
- `review required` — штатный результат структурной правки, а не успешная синхронизация и не подтверждение parity. Читать `pixso-sync-report/report.json`; реальные ошибки токена, конфликт палитры, неизвестные токены, ошибки сборки разбирать по логам. Не глушить тесты или обходить защиту. При ошибке проверить, что запуск относится к нужному commit.
- Артефакт `pixso-sync-input` содержит plan.json, manifest.json, PNG, XML и layout.json. Сверить все затронутые состояния, включая новые, при необходимости дополнительные сценарии. Не использовать данные личных аккаунтов; только изолированный fixture.
- `accept_structure=true` допустим исключительно после проверки реализованных структурных изменений обеих сторон и отсутствия конфликтов. Это не status=verified. Обновлять last_verified с фактическими хэшами только после визуальной проверки соответствующего захвата. Если проверка не завершена — draft и конкретные расхождения.
- При новом зарегистрированном target старый baseline закономерно отличается. Не переписывать baseline ради зелёного CI. Не восстанавливать удалённые фреймы и не создавать дубли из входных скриншотов.

## Короткие команды

- «Обнови интерфейс: …» — применить задачу в коде и Pixso.
- «Синхронизируй макет» — сравнить beta, live Pixso, baseline и последний capture; перенести code → design с сохранением ручных правок.
- «Перенеси изменения из Pixso» — design → code; затем обновить связанные компоненты, реестр и проверить CI.
- «Проверь все экраны» — найти отсутствующие/устаревшие состояния, исправить в обоих проектах, расширить capture coverage.
- «Собери beta» — выполнить проверку текущих изменений и запустить beta-релиз.

## Уточнение текущего проекта

По решению пользователя от 28.11.2026 отдельный ручной прогон TalkBack не является обязательным критерием этого UI/UX-аудита. Не удалять имеющиеся semantics, подписи, состояния выбора и минимальные размеры нажатия. Проверки контраста, масштабирования шрифта, размеров экрана и клавиатуры остаются в плане.
