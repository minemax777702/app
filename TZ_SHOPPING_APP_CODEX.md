## 0. Цель, границы и исходные условия

Развить существующее Android-приложение, использующее Kotlin, Jetpack Compose / Material 3, Room, Coroutines/Flow, Glance и QR-синхронизацию, до приложения с товарами **только из «Ленты»**, расчётом расходов, удобными карточками и BottomSheet, компактным архивом, историей цен и расширенной аналитикой. Интеграция с «Лентой» уже существует через `https://mcp.lenta.com/mcp` (`storefront_products_search`, `storefront_product_details`, канал `locc`); использовать её и проверить реальные форматы ответа по коду и тестам перед изменениями, не придумывать поля API.

**Предположение о развёртывании:** новая, чистая установка. Не требуется поддерживать старые пользовательские базы, старые активные списки, архивы и резервные копии, миграцию с версий до новой схемы, а также обратную совместимость старого QR-формата. Однако **новые** списки, архив, история, экспорт/импорт и QR-обмен должны работать с новой моделью данных. Если код содержит исторические миграции, их можно удалить/пересобрать только после проверки сборки и актуальной конфигурации Room; не делать вид, будто версии v9 и v10 одновременно актуальны. В описании текущей реализации указана **Room v10**, тогда как карта проекта содержит устаревшую v9. Проверить реальную версию в репозитории.

**Не входит в объём:** фактическое подтверждение цен чеком, онлайн-заказ, оплата, формирование корзины «Ленты», штрихкод-сканер, несколько параллельных пользовательских списков, ручное создание несуществующего товара. Важно: «цена на момент покупки» в этом ТЗ — **зафиксированная приложением цена из витрины «Ленты» при отметке покупки**, а не доказанная кассовая цена.

**Сохранить, если не заменено явно:** отметку всей строки купленной при коротком нажатии; свайп на удаление; Undo; количества 1–999; завершение списка (автоматическое и ручное с сохранением непокупленных); архив и повтор покупок; профиль и идентификаторы покупателей; светлую/тёмную темы; QR-обмен, новые резервные копии; виджет и голосовой ввод — в пределах, совместимых с запретом произвольных товаров. Пользовательский интерфейс — русский.

### Общие технические правила

1. Источник идентичности товара — **стабильный ID «Ленты»**, а не нормализованное имя. Название, изображение и фасовка — атрибуты, которые могут меняться. Не объединять разные товары с одинаковым именем и не создавать дубль одного ID; при необходимости однозначно использовать составной ключ, если интеграция выдаёт не глобальный ID.
2. Данные о цене: хранить сумму в **копейках** (`Long`), а не `Float`/`Double`. Цена nullable, валюта RUB, тип цены (`card`, `promo`, другой/неизвестный), источник, адрес/витрина/канал, время получения и актуальность; не подменять цену чужого адреса текущей. Для вычислений и графиков явно различать неизвестную цену и 0 ₽.
3. Цена **по карте** — предпочтительный отображаемый показатель главного списка. Если API не возвращает её отдельно, не выдавать `promo` или обычную цену за цену по карте: показывать «Цена по карте неизвестна» / доступную отдельно маркированную цену только там, где это явно предусмотрено. Перед реализацией проверить возможность получения `card` в реальном контракте текущего клиента.
4. Для будущей аналитики сохранять неизменяемые снимки фактического события отметки покупки: `productId`, название, `unitPriceKopecks?`, тип цены, количество, итог позиции?, время покупки, ID покупателя, ID похода; к каждому событию привязать идентификатор, чтобы не дублировать записи при sync/backup. При цене неизвестной `lineTotal` также неизвестен. Список и архив не должны задним числом менять цену этих событий при обновлении каталога.
5. Проектирование и реализация — в существующих слоях: UI/Compose → ViewModel/Flow → Repository/DAO/Room; сетевой клиент отдельно. Не выполнять сеть в Composable и не блокировать UI; стабилизировать долгие запросы, Debounce и отмену старых результатов.
6. Для каждого этапа предусматривать пустые/ошибочные/офлайн-состояния, а также поддержку светлой и тёмной тем, масштабирования текста, системных отступов и TalkBack.
7. По умолчанию не удалять работающую функциональность без указания ТЗ. При конфликте требований следовать **позднейшим уточнениям** в настоящем ТЗ.

В 01–06 разрешается временно поддерживать исходную модель, если иначе приложение перестанет собираться. При последующей переработке удалять временный код, фиксируя это в журнале.

## 2. Функциональные требования и приёмка по этапам

### ЭТАП 01 — Общая стоимость списка и оставшийся бюджет

**Текущее поведение:** количество 1–999 хранится, но стоимость всего списка и его остатка не вычисляются; цены «Ленты» могут быть неизвестны или сохранены для адреса.

**Что сделать:**
- На главном экране отображать **«Общая стоимость»** всех позиций и **«Осталось купить на»** только для некупленных позиций. Третьим, необязательным показателем можно показать «Куплено на»; не заменять им обязательные два.
- Формула: `lineTotal = unitPriceKopecks × quantity`; `total = Σ lineTotal` для всех позиций; `remaining = Σ lineTotal` только для ещё не купленных. При отметке покупки `total` неизменен, `remaining` уменьшается; при отмене — восстанавливается. При изменении количества и удалении пересчитать оба показателя по текущему состоянию; изменения не должны требовать перезапуска.
- Если есть товары без известной подходящей цены, показывать **сумму известных позиций + признак неполноты**, например «от 540,00 ₽ · 2 товара без цены» (для обеих сумм со своими количествами). **Не** подписывать частичный итог как точный «Итого». Если все цены известны, показать обычную сумму. Если нет ни одной известной цены — «Стоимость неизвестна».
- При загрузке и обновлении цен пересчитывать состояние автоматически. Применять только цену текущего адреса/канала; сохранённую цену можно показывать с честной меткой об устаревании. Точность расчёта: копейки, форматирование `ru-RU`.
- Добавить в модель событие цены покупки, достаточное для этапов 08–10 (см. общие правила); если окончательная схема будет меняться на этапе 07, обозначить переходный код.

**Приёмка:** 3×100 ₽ + 2×50 ₽ = 400 ₽; после покупки первой позиции остаток 100 ₽, общая стоимость 400 ₽; удаление второй позиции корректно снижает общий итог; Undo и количество пересчитывают моментально; неизвестная цена не приводит к ложному точному итогу; после пересоздания экрана показатели согласованы с БД.

### ЭТАП 02 — Главный экран: компактные карточки

- Убрать круглый чекбокс слева. На его месте показывать превью товара из «Ленты»; при отсутствии картинки — нейтральный placeholder такой же геометрии (позднее все новые товары должны быть из «Ленты»).
- Название в карточке можно ограничить 1–2 строками; полное название будет доступно в этапе 03.
- **Не показывать остатки на складе** в главной карточке (данные наличия могут остаться в сервисном слое, если нужны в других местах).
- Показывать цену **по карте «Ленты»** с явным указанием «по карте»; неизвестную не подменять. Цена относится к **одной единице**, а стоимость всей позиции рассчитывается как цена × количество (в сводке этапа 01).
- Сделать кнопки `−` и `+`, а также поле/индикатор количества заметно крупнее и удобнее для нажатий; целевой touch target **не менее 48 dp**, визуальные размеры проверить по фактической ширине карточки; при тесной ширине допустить адаптивное расположение без перекрытия названия/цены.
- Короткий тап по свободной области карточки отмечает всю позицию купленной; кнопки изменения количества, миниатюра (если сделана отдельная функция), Swipe и Undo не должны случайно срабатывать как покупка. После покупки сохранить визуальное различие купленной позиции без старого чекбокса.

**Приёмка:** на типичном телефоне текст и контролы не перекрываются; отсутствие картинки и цены не ломает вёрстку; TalkBack озвучивает состояние куплено/не куплено; все жесты корректны.

### ЭТАП 03 — Полная информация по удержанию более 3 секунд

- При **непрерывном удержании карточки более 3000 мс** открывать `ModalBottomSheet` с полным названием без обрезки, крупным изображением, ценой и её типом/актуальностью, фасовкой, штрихкодом или другими реально доступными метаданными, количеством в списке; поля без данных скрывать или подписывать как неизвестные.
- Считать 3000 мс от `pointer down`. **Ровно 3000 мс ещё недостаточно**; реагировать на переход порога. Открыть **один раз** за удержание. Если пользователь начал горизонтальный свайп/вертикальную прокрутку, жест отменить по touch slop; не открывать шторку через 3 с во время прокрутки.
- После длительного удержания отпускание пальца **не** отмечает товар купленным. Короткий тап продолжает покупать. Элементы изменения количества/Undo не запускают долгое удержание всей строки.
- Данные детали брать из локального состояния, свежие детали при запросе обновлять асинхронно; сетевой сбой не должен блокировать шторку.

**Приёмка:** удержание 2,9 с не открывает; >3 с открывает; отпускание не покупает; свайп удаления работает; длинное имя полностью видимо и прокручивается.

### ЭТАП 04 — Единый стиль BottomSheet вместо всех внутренних модальных окон

- Заменить все **внутриприложенческие** диалоги на `ModalBottomSheet` Material 3, стилизованные как текущая шторка «Добавить товар»: верхняя ручка, заголовок, закрытие, отступы, скругления, правильная цветовая схема и обработка клавиатуры. Создать общий компонент/обёртку и переиспользуемые шаблоны действий.
- Аудит обязателен для: обязательного имени первого запуска; переименования профиля; магазина/адреса; нового/редактируемого продукта (позже сценарий изменится в 07); удаления продукта; деталей продукта; подтверждения удаления архива; «Что передать»; выбора владельца восстановленной копии; «Локальные копии»; подтверждения отмены обмена; прочих `AlertDialog`/`Dialog` из актуального дерева исходников.
- Для **обязательной** формы первого запуска запрещено закрытие по фону, Back и свайпу, пока не введено имя; доступна только валидная кнопка продолжения.
- Для разрушительных операций сохранить подтверждение и явные кнопки «Удалить/Отмена»; для ввода — корректное поведение IME, скроллинг над клавиатурой и сохранение состояния при повороте/пересоздании (в пределах выбранной архитектуры).
- **Исключение:** системные UI Android (разрешения, клавиатура, SAF / выбор файла) остаются системными. **Полноценные страницы** (список, архив, статистика, настройки) не превращать в шторки.

**Приёмка:** в коде больше нет пользовательских диалогов старого вида, за исключением явно обоснованных системных компонентов; все доступные ранее действия работают; тёмная тема и Back корректны; обязательная форма не закрывается раньше времени.

### ЭТАП 05 — Новая навигация и единый экран настроек

- На нижней панели заменить три отдельные кнопки: «База продуктов», «Синхронизация», «Магазин Ленты» — одной кнопкой **«Настройки»** с шестерёнкой.
- **Сохранить отдельную кнопку «Архив списков» / история покупок рядом с кнопкой «Настройки»**, а не переносить в настройки. Сохранять её прежнее условие доступности при наличии архива, если это не ухудшает доступ к архиву; «Завершить список» и большой `+` тоже остаются.
- Экран «Настройки» — **полноценная страница** с Back и **ровно двумя вкладками**:
  1. **«База продуктов»** — локальная база, поиск, карточки, добавление.
  2. **«Синхронизация и магазин»** — единый прокручиваемый экран с адресом/витриной «Ленты», QR-обменом, локальными и файловыми копиями, профилем.
- Никакой отдельной вкладки «Магазин». Адрес можно редактировать на совмещённом экране (если нужен отдельный BottomSheet для ввода, он следует этапу 04). Не терять существующие действия QR, экспорт/импорт, отмену синхронизации и настройки копий.
- При выходе и возвращении на страницу разумно сохранять выбранную вкладку, но вход из контекстного действия «Укажите адрес» должен сразу открывать нужную вкладку и прокручивать к настройке адреса.

**Приёмка:** на главном экране доступен один переход в настройки, отдельный архив рядом; две вкладки; все бывшие точки входа находят соответствующий функционал; системный Back работает ожидаемо.

### ЭТАП 06 — Удобный поиск в «Добавить товар»

- Убрать горизонтальные **текстовые подсказки** под полем и блок предпросмотра распознанных названий, если он воспринимается как подсказка. Не путать с обязательными сообщениями об ошибках и состоянии; их сохранить.
- Удалить заголовок **«ТОВАРЫ ЛЕНТЫ»**; оставлять результаты без отдельной шапки. Убрать из каждой карточки «В базу» и «+ В список».
- **Тап по всей карточке результата** сразу добавляет выбранный товар в текущий список **и сохраняет карточку в локальной базе** (ID, название, изображение, цена, фасовка и прочие доступные метаданные); повторный товар по ID не добавлять повторно, показать понятное уведомление. Успешный сценарий совместим с существующим очищением поля.
- Увеличить полезную высоту BottomSheet, ориентир — почти весь экран с учётом status/navigation bars и IME. Результаты занимают доступную высоту и имеют собственную прокрутку.
- **Прокрутка результатов вверх и вниз не должна тянуть/закрывать BottomSheet**. Закрытие перетаскиванием разрешить **только за верхнюю ручку/верхнюю отдельную зону шторки**; достижение верхнего/нижнего края результатов не передаёт жест закрытия родителю. Явный крестик и Back сохраняются. При необходимости отключить стандартный drag всей шторки и реализовать отдельную зону для drag-to-dismiss, не ломая accessibility.
- Ввод и голосовой поиск могут оставаться, но итогом выбора должен быть **конкретный товар «Ленты»**; после этапа 07 нельзя добавлять произвольное распознанное название без привязки к товарному ID.
- Сохранять debounce запросов, загрузку/ошибки/пустой ответ, защиту от устаревших ответов; в режиме офлайн можно выбирать ранее сохранённый товар, но не выдумывать данные.

**Приёмка:** скролл выдачи в обе стороны не закрывает шторку; перетаскивание за ручку явно закрывает; тап по товару добавляет и сохраняет, без кнопок; уведомление о дубле; клавиатура не перекрывает выдачу.

### ЭТАП 07 — Только продукты «Ленты» и локальная база

- Удалить возможность ручного создания/переименования произвольных товаров, встроенный каталог `res/raw/products.txt` как источник пользовательских продуктов, персональную генерацию названий по истории и всю бизнес-логику **локальных продуктов без ID «Ленты»**. Удалить/очистить неиспользуемые классы, ресурсы и методы после поиска usages и обновления тестов. «Локальная база» далее означает **локально сохранённый каталог товаров «Ленты»**, а не ручные товары.
- Экран **«База продуктов»**: поиск **только по БД устройства** среди сохранённых продуктов «Ленты»; без сетевого запроса на каждую букву. Поиск по имени, можно дополнительно по штрихкоду/фасовке при наличии; сортировка предсказуема. Пустое состояние и счётчик сохранённых товаров.
- Кнопка **«Добавить продукт»** открывает BottomSheet из этапа 04. Внутри — поиск по **MCP «Ленты»**, а не по собственной БД (локальные совпадения можно пометить как «Уже в базе»); тап по найденной карточке **сохраняет её в локальную базу**, но **не добавляет в текущий список** — это принципиальное отличие от этапа 06.
- Сохранять ID, полное имя, URL/кэш превью, упаковку/фасовку, цену и тип цены, время обновления, адрес и канал, штрихкод если API отдал. Сетевое обновление существующего ID выполняет upsert. Удаление из базы — с подтверждением BottomSheet; не стирать уже зафиксированные исторические покупки/архивные снимки.
- Активный список и новые записи архива связывать по ID товара «Ленты». Два разных ID с одинаковым названием допускаются; один и тот же ID второй раз в текущий список не добавлять (количество меняется через `+/-`).
- При отсутствии настроенного адреса и сети давать понятные состояния, переход на вкладку «Синхронизация и магазин», не использовать цену другого адреса как действующую.
- **Новая чистая схема БД:** убрать устаревшие сущности и prefs, связанные только с ручными товарами, и определить единственный источник правды для каталога и цен. Изменить DAO, Repository, ViewModel, импорт/экспорт новых копий, QR-модель/merge, тесты, а также обновление виджета. Не требуется поддерживать старые форматы. **Новый** формат backup и QR должен переносить необходимые ID и снимки покупок; в отношении фото достаточно переносить URL, кэш восстанавливать асинхронно. Не добавлять изображения в QR в бинарном виде.
- Голосовой ввод после распознавания должен предлагать найденные товары «Ленты» для выбора; не сохранять свободно распознанную строку как самостоятельную позицию.

**Приёмка:** на чистой установке нельзя создать свободный товар; из базы онлайн-поиск сохраняет товар, но не покупает его; из «Добавить товар» выбор сразу добавляет в список; локальный поиск работает без сети; дубликаты проверяются по ID; свежие QR и backup после передачи создают полноценные карточки без потери цены/идентичности/истории, кроме ожидаемого кэша изображений.

### ЭТАП 08 — Компактный архив и цена на момент покупки

- Сохранить существующую структуру архивных списков, даты, раскрытие, выбор позиций, «Купить снова», удаление и учёт покупателей.
- В **основном развёрнутом списке архивных товаров** убрать миниатюры и дополнительные громоздкие поля; показывать компактное **название**, сохраняя элемент выбора для повторной покупки и отдельную иконку **«Информация»** рядом. Длинные названия в строке можно ограничить, но в деталях — полностью. В свёрнутом состоянии оставить нынешний краткий список имён.
- Нажатие кнопки «Информация» открывает BottomSheet (этап 04) с **полным названием, превью, количеством, ценой за единицу на момент покупки и стоимостью позиции**. При неизвестной цене так и писать, не брать актуальную вместо исторической. Можно показывать дату/покупателя, если доступны.
- При отметке купленным **фиксировать snapshot цены** (из подходящего на тот момент ответа/кэша с честной меткой времени), количества и имени. В архиве хранить snapshot, не ссылаться на изменяемое текущее значение. Не допускать двойных покупок при автоматическом завершении, undo, повторном архивировании или QR-слиянии.
- Временная семантика: датой покупки считается **момент отметки позиции купленной**, а не момент завершения списка. Для ручного завершения отметки ранее купленных товаров остаются неизменными.

**Приёмка:** изменение текущей цены после покупки не меняет подробности старого архива; доступна полная информация; строка архива компактная и без миниатюры; повтор покупки сохраняет количество и создаёт новую будущую покупку (без автоматического копирования старой цены как текущей).

### ЭТАП 09 — Расширенная статистика и графики

- Оставить работоспособными существующие показатели количества списков/товаров, среднюю длительность похода, активность, любимый день и фильтр по пользователю там, где он уже есть.
- Добавить: **все расходы за время**, расходы за выбранный период, среднюю стоимость одного похода, **самый дешёвый** и **самый дорогой** купленный товар (по цене **за единицу** на зафиксированном событии, с датой и названием), количество покупок/единиц; не путать число позиций, штук и походов.
- Разместить графики: динамика расходов по дням/неделям/месяцам; сравнение периодов; динамика цены выбранного товара; топ товаров по сумме расходов; частота покупок, а также диаграмма распределения расходов по товарам. Нужна адаптация для узких экранов, подписанные оси, читаемые числа и отображение пустых периодов без фиктивных расходов.
- Блок **«Чаще всего покупаю»**: рейтинг по **количеству отдельных походов**, содержащих товар, а не по сумме штук; отдельно показывать сколько единиц куплено. Фильтр периода и пользователя применять к рейтингу. Нажатие на товар открывает подробную историю с ценами (этап 10).
- Периоды: «Неделя», «Месяц», «Год», «Всё время» (или эквивалент с понятными датами) и детализация графика по дням/неделям/месяцам; не допускать несогласованных выборок на соседних карточках.
- Суммы агрегировать только по событиям с известной ценой; при наличии неизвестных выводить предупреждение **«Неполные данные о расходах: N покупок без цены»**. Средние и экстремумы считать только по известным данным, показывая это в подписи. Для периода без завершённых списков корректно показывать пустое состояние.
- **Одна покупка** = одно подтверждённое событие покупки позиции; **поход** = архивный список/идентификатор похода. Для продолжающегося незавершённого списка учитывать уже отмеченные покупки **один раз**, согласованно с архивом после завершения, если в коде история их учитывает. Даты вычислять по локальной календарной дате пользователя с устойчивыми timestamp в БД.

**Приёмка:** суммы графиков совпадают с суммой событий за тот же период; фильтр пользователя не меняет данные другого; одинаковый товар в трёх походах с количествами 2, 1, 5 имеет частоту 3, количество штук 8; неизвестные цены не превращаются в 0 ₽; изменение цены в каталоге не переписывает историю расходов.

### ЭТАП 10 — Подробная история конкретного товара

- В шапке экрана деталей вместо длинного названия использовать **фиксированный заголовок «Информация о товаре»**. Полное название показать ниже в контенте, без обрезки, с переносами строк.
- В верхней части содержимого показать **«Средний интервал покупок»** и количество дней с покупками; при одной дате пояснить, что интервал пока неизвестен. Интервал вычислять между **различными календарными днями** покупок, а не между несколькими покупками в один день.
- Показывать историю **каждого события покупки**, сохраняя отдельные записи даже в один день: дата и по возможности время, цена за единицу на тот момент, количество, стоимость позиции, покупатель при наличии. Для неизвестных цен выводить явный статус.
- Добавить график **«Динамика цен»** по датам (при нескольких покупках в один день показывать точки со временем или однозначное дневное агрегирование с подписью способа), минимум/максимум/среднюю цену за период и историю изменений. Различать цену по карте, акционную и неизвестную; не сравнивать без маркировки разные типы цен. График не должен подтягивать текущую цену вместо исторической.
- Навигация из истории продуктов и из рейтинга «Чаще всего покупаю» должна открывать один и тот же экран по `productId`, а не по одному названию.

**Приёмка:** длинное имя не растягивает шапку; две покупки одного товара за день видны отдельными событиями; интервал корректен; график и показатели рассчитываются по сохранённым покупкам; перезапуск приложения ничего не теряет.

## 3. Единая модель данных — целевое состояние после этапа 10

Это **контракт поведения**, не требование дословно назвать таблицы. Codex выбирает нормализованную Room-схему в соответствии с проектом и документирует итоговые имена в журнале.

| Сущность | Обязательные сведения | Примечание |
|---|---|---|
| `LentaProduct` | внутренний ключ, `lentaProductId`, имя, previewUrl?, pack?, barcode?, updatedAt | локальный каталог сохраняемых товаров «Ленты» |
| `ProductPrice` / cached price | productId, цена в копейках?, priceType, address/store context, channel, fetchedAt | можно встроить в карточку при одной витрине; не использовать чужой адрес |
| `ShoppingItem` | UID, productId, quantity 1..999, isBought, purchasedAt?, buyerId?, priceSnapshot? | одна позиция на productId в текущем списке |
| `PurchaseEvent` / archive item | стабильный UID события, productId, nameSnapshot, quantity, unitPrice?, priceType?, lineTotal?, purchasedAt, buyerId, tripId | **неизменяемый** snapshot для архива/истории/статистики |
| `Trip` / archive list | UID, finishedAt, связанные события, время похода | архив и повтор покупок |
| `User` | стабильный ID и имя | профиль / синхронизация |
| `SyncSnapshot` | новые идентификаторы и все необходимые события | корректное объединение без дублей |

**Важно о моменте покупки и Undo:** до истечения окна отмены событие считается предварительным; после подтверждения сохраняется единожды. Если покупка уже отражается в статистике незавершённого списка, один и тот же UID переносится в архив без создания второй записи. Если реализация текущего кода устроена иначе, предложить эквивалентное транзакционное решение и зафиксировать его в `CODEX_PROGRESS.md`.

**Потенциальная неоднозначность требований:** пользователь хочет цену **по карте**, но API иногда может возвращать цену типа `promo` или не возвращать `card`. Нельзя автоматически считать это ценой по карте. Реальное правило выбора цены реализовать по контракту API; при отсутствии `card` цена по карте неизвестна. Для архивных/аналитических данных сохранять тип цены каждого снимка; если единичная цена получена не по карте, честно подписывать тип.

7. При неясности, которую нельзя решить по ТЗ и исходникам, зафиксировать точную альтернативу в «Решения и допущения», выбрать самый безопасный вариант без потери данных и с явной UI-маркировкой; не переопределять требования молча. Для действительно блокирующего решения пометить `BLOCKED` и изложить вопрос пользователю.
8. **Отчёт по итогам этапа:** номер, список реализованного, затронутые файлы, проверенные команды с результатом, известные ограничения, номер следующего этапа. Не писать «всё готово», если выполнена только часть.

## 6. Итоговая приёмка проекта (после этапа 10)

- [ ] Чистая установка работает: имя/профиль, адрес «Ленты», поиск, сохранение реального товара, добавление в список.
- [ ] Только товары «Ленты», идентичность по ID; поиск в базе локальный, поиск нового — через MCP.
- [ ] Общая и оставшаяся стоимость меняются при покупке/Undo/удалении/изменении количества и корректно маркируют неизвестные цены.
- [ ] Главный список показывает миниатюру вместо чекбокса и цену по карте без остатков; количество удобно менять.
- [ ] Долгое удержание **>3 с** открывает детали и не совершает покупку.
- [ ] Внутренние модальные окна заменены BottomSheet; экран настроек содержит две вкладки; история рядом с настройками на главном экране.
- [ ] В добавлении товара карточки кликабельны; нет кнопок «В базу» / «+ В список», заголовка «ТОВАРЫ ЛЕНТЫ» и текстовых подсказок; скролл выдачи не закрывает шторку.
- [ ] Архив компактен, детали товара содержат **исторические** цену, фото, полное имя, количество.
- [ ] История продукта хранит каждую покупку, интервал, количество, дату и график изменения цен; шапка фиксированная.
- [ ] Расширенная статистика показывает расходы, графики, крайние цены, рейтинг «Чаще всего покупаю», фильтрацию и корректную неполноту данных.
- [ ] Новые backup/QR и виджет работают с новой схемой, не дублируют события покупок.
- [ ] Unit-тесты и релизная сборка проходят; ограничения инструментального тестирования документированы.
- [ ] `CODEX_PROGRESS.md` содержит результаты **всех десяти этапов**, `CODEX_HANDOFF.md` содержит итоговый статус и хеш коммита.
